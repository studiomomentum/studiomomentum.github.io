# 콘텐츠 관리 캐시 (2026-09-30)

## 확인한 원인

기존 open()은 메모리 data를 재사용하므로 동일 페이지 내 탭 전환 캐시는 있었다. 새로고침하면 사라졌고 콘텐츠 탭을 처음 열어야 서버 조회를 시작했다. 운영 content.get 단일 읽기 측정은 약 2,874ms / 65,145 bytes였다. 전체 로딩 시간이나 평균값으로 일반화하지 않는다.

## 적용

- 인증된 대시보드 초기화 시작 시 콘텐츠를 미리 조회한다. 다른 대시보드 로딩을 기다리지 않는다.
- 같은 로그인 세션에 한해 sessionStorage에서 서버에 저장된 콘텐츠와 선택 주제를 복원한다. 30분 지난 캐시는 사용하지 않으며 캐시로 먼저 표시한 뒤 최신 상태를 백그라운드에서 확인한다.
- 로그인 세션 토큰의 SHA-256으로 캐시 범위를 구분한다. 비밀번호·토큰 원문을 콘텐츠 캐시에 추가 저장하지 않는다. 로그인 변경·만료·로그아웃 때 캐시와 메모리 화면을 비운다. 비공개 콘텐츠를 localStorage나 공개 파일에 저장하지 않는다.
- 동시에 발생한 content.get 요청은 하나로 합친다. 저장·검수·생성·전송 응답이 오면 서버 스냅샷으로 캐시를 갱신한다. 미저장 입력은 캐시에 기록하지 않는다.
- 배경 조회는 입력 중인 글을 덮어쓰지 않는다. 응답 내용이 같으면 DOM을 다시 그리지 않는다. 기존 생성 진행 막대·완료 감지·전송 상태·키워드 부분 갱신은 유지한다.
- 첫 방문이나 캐시 만료 후의 서버 조회 시간 자체가 제거되는 것은 아니다. 캐시는 인증을 대신하지 않는다.

## 검증

- 실제 Chrome: 메모리 탭 재사용, 새로고침 후 서버 응답 전 캐시 표시, 미저장 문구 캐시 제외, 동시 조회 1건, 최신 결과 반영, 배경 응답 시 편집 보존, 다른 세션 캐시 거부, 로그아웃 후 늦게 도착한 응답 무시.
- 제어된 테스트의 캐시 표시 약 13~14ms. 운영망 체감 속도와 구분한다.
- 기존 관리자 콘텐츠 UI 회귀(모바일/매체별 생성/진행 표시/편집·검수·전송) 통과.
- 실제 인증 모듈에서 세션 만료 응답 시 캐시 삭제·캐시 범위 해제 확인. 기존 타깃/발굴/유입 관리자 화면 회귀도 Chrome에서 통과.
- 운영 배포 확인 중.
